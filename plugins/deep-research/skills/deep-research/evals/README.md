# Набор проверок скилла

Зачем: без замера нельзя сказать, помогла ли правка скилла. Для старта хватает двух-трёх десятков задач из реальных провалов (так советует Anthropic в «Demystifying evals for AI agents»); набор растёт по мере того, как находятся новые провалы.

## Что внутри

| Файл | Что |
|---|---|
| `cases.jsonl` | 14 сквозных кейсов: скилл отвечает на вопрос целиком. У кейса есть происхождение (какую ошибку он ловит), режим, ключевые факты, известные ошибки, ожидаемое поведение, эталонный первоисточник |
| `verifier_cases.jsonl` | 10 кейсов для проверяющего фазы 6: одно утверждение и ожидаемый вердикт |
| `graders/` | три оценщика: опора на источник, покрытие, качество источников |
| `score.py` | механические подсказки по отчёту, сборка промптов оценщиков и проверяющего, сверка вердиктов, итог прогона |
| `run_e2e.py` | прогон одного сквозного кейса через `claude -p` с выбранной версией скилла |
| `gemini_verifier.py` | необязательно: тот же проверяющий на Gemini, для сравнения моделей разных семейств (нужен `GEMINI_API_KEY`) |

Что ловят кейсы:
- E01, E02: правовая фактура (устаревшие нормы, неверная посылка вопроса «ЦБ утверждает»).
- E04, E05: ложное «на странице этого нет» от сводки WebFetch; ссылка на руководство, данная без чтения.
- E06, E07, E08: доля, приписанная не той категории; пропущенная оговорка источника; цифра с графика, выданная за цитату.
- E09: Reddit (встроенные инструменты туда не пускают).
- E10, E12: свежесть против знаний модели, цены по документации.
- E11: честное «не найдено этим поиском» вместо выдуманного исследования.
- E13: узкое поле ответа: вопрос «что делать» исследуется под первый пришедший в голову вариант, остальные ветки не рассматриваются.
- E14, E15: постановка вопроса (фаза 1): запрос без решения-адресата и заряженный вопрос «докажи, что». Прогон идёт без человека, поэтому проверяется автономная ветка; сами уточняющие вопросы гейта в `claude -p` не проверить, их смотрят руками в живом запуске.
- V01–V10: частичная правда, умолчание, отрицание, цифра с графика, модальность («рекомендует» против «запрещает»), контрольный верный случай против ложных отказов.

## Как гонять

Результаты держите вне репозитория, например `RUN=~/evals-runs/$(date +%Y%m%d)_<метка>`, где метка называет проверяемую правку.

1. **Проверяющий** (дёшево, минуты): для каждого `V01`…`V10` взять промпт `python3 score.py verifier-prompt --case V01`, отдать отдельному субагенту, его строку JSON дописать в `$RUN/verifier/results.jsonl`. Сверка: `python3 score.py verifier-score --results $RUN/verifier/results.jsonl`.
2. **Сквозные кейсы** (дорого, 10–40 минут на кейс): `python3 run_e2e.py --case E06 --trial t1 --run $RUN`. Для сравнения версий разверните старую через `git worktree add /tmp/dr-old <коммит>` и передайте `--skill-dir`. Минимум два прогона на кейс и версию.
3. **Механика:** `python3 score.py check --case E06 --report $RUN/E06/t1/report.md` показывает, где искать ключевые факты и известные ошибки. Это подсказки, не оценка.
4. **Оценщики вслепую:** переложите отчёты под случайными именами (путь выдаёт версию), каждому отчёту три отдельных оценщика с промптами `python3 score.py judge-prompt --case E06 --report … --grader coverage` (и `groundedness`, `source_quality`). Их строки JSON в `…/grades.jsonl` рядом с отчётом.
5. **Итог:** `python3 score.py summary --run $RUN`.
6. **Прочитайте 2–3 транскрипта**, прежде чем объявлять улучшение. Разброс между двумя прогонами одной версии бывает 0,1 по опоре на источник; разница меньше разброса не является эффектом.

## Правила набора

- Кейс добавляется из реального провала; в `origin` что случилось.
- Эталон сверен с первоисточником до добавления, в `ground_truth` публичная ссылка.
- Вопрос кейса не подсказывает ответ; `key_facts` и `known_errors` скилл не видит.
- Не вписывайте ответ кейса в правила скилла: замер покажет подгонку, а не улучшение.
- Правовые эталоны устаревают, перед прогоном сверяйте.
